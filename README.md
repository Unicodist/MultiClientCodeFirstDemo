# MultiTenantDemo: database-per-tenant POC

A proof of concept for an enterprise multi-tenant architecture on .NET 10, ASP.NET Core and EF Core 10 Code
First, with one SQL Server database per tenant, tenant metadata from an external registry, stored procedures
deployed through EF Core migrations, and migration SQL generated by `dotnet ef`.
Migrations are applied by hand. Code carries no comments by convention; this README is the documentation.

> [!WARNING]
> **There is no authentication.** The tenant comes from the `X-Tenant-Id` request header, which is a routing
> input only: any caller can claim to be any tenant. Run the API on a developer machine or an isolated test
> network only. Outside the `Development` environment it refuses to start unless
> `Security:AcknowledgeUnauthenticatedTenantHeader=true` is set, and it binds to `localhost` by default.
> Production needs the tenant derived from, or authorized against, an authenticated identity.

## Integration points

| Integration point | Interface | What ships today | Real application |
|---|---|---|---|
| Tenant registry | `ITenantRepository` | `TenantRepository`: tenants and their connection strings are rows in the system database's `system.Tenants` table. | Same table, or an adapter over the external tenant service. |
| Tenant databases | none | Databases (and their initial catalog) must already exist. Nothing in the code creates or migrates them. | Created by whatever provisions tenants. |
| Applying migrations | none | You run the generated SQL (or `dotnet ef database update`) yourself. | Your deployment process. |

Other assumptions: SQL Server 2016 SP1 or later (`CREATE OR ALTER PROCEDURE`), tenant ids are lower-case
`[a-z0-9-]`, up to 64 characters (`TenantId.IsValid`), and CI is GitHub Actions.

## Architecture

Two EF Core contexts, both configured with the fluent API (`IEntityTypeConfiguration<T>` classes, no data
annotations on entities), each with its own migrations:

| Context | Database | Contents | Migrations |
|---|---|---|---|
| `ClientDbContext` | One per client (tenant) | `dbo.Customers`, `dbo.GetCustomerSummary` | `MultiTenantDemo.Client.Data/Migrations`, SQL in `migrations/client` |
| `SystemDbContext` | One shared system database | `system.Tenants` | `MultiTenantDemo.System.Data/Migrations`, SQL in `migrations/system` |

Project references: `Api` references `Client.Data` and `System.Data`; `Client.Data` references `Client.Domain`;
`System.Data` references `System.Domain`. Services live in the Domain projects and depend only on repository
interfaces declared there (`ICustomerRepository`, `ITenantRepository`); the Data projects implement those
interfaces with the DbContexts and bind them in `AddClientData` and `AddSystemData`, and `Api` registers the
Domain services. `Client.Data` knows nothing about tenancy: it asks an
`IClientConnectionStringProvider` for the connection string, which `Api` implements with the tenant resolver.

```text
src/
  MultiTenantDemo.Api               Startup project. Controllers, error mapping, the X-Tenant-Id TenantResolver and
                                    connection validation (TenantInfoFactory). Never migrates.
  MultiTenantDemo.Client.Data       ClientDbContext, fluent configurations, migrations, embedded .sql files,
                                    CustomerRepository.
  MultiTenantDemo.System.Data       SystemDbContext, fluent configurations, migrations, TenantRepository.
  MultiTenantDemo.Client.Domain     Customer entity, customer contracts, ICustomerRepository, CustomerService.
                                    No dependencies.
  MultiTenantDemo.System.Domain     Tenant entity, TenantInfo, ITenantRepository, ITenantResolver. No dependencies.
migrations/
  client/                           SQL generated by dotnet ef for ClientDbContext migrations, git-ignored.
  system/                           SQL generated by dotnet ef for SystemDbContext migrations, git-ignored.
scripts/
  add-migration.cs                  Runs dotnet ef migrations add for one context and strips EF's comment lines.
  generate-migration-sql.cs         Runs dotnet ef migrations script for both contexts into migrations/.
tests/
  MultiTenantDemo.IntegrationTests  Real SQL Server (Testcontainers or an existing disposable server).
```

### Request flow (API)

1. `TenantResolver` (scoped) reads `X-Tenant-Id`, rejects missing or malformed values, and looks the tenant up
   through `ITenantRepository`. Unknown and inactive tenants are rejected.
2. `TenantInfoFactory` validates the registry's connection metadata and fails closed: the server must be on
   `TenantConnections:AllowedServers`, the database name must match a strict pattern and must not be a system
   database, and `TrustServerCertificate` is refused unless explicitly allowed (development only).
3. The resolved `TenantInfo` (tenant id, non-secret `DatabaseKey`, secret connection string) is cached for the
   request. Callers can never supply a connection string.
4. `ClientDbContextFactory` (scoped) creates a fresh `ClientDbContext` per operation; repositories dispose it.

| Situation | Response |
|---|---|
| Missing or malformed `X-Tenant-Id` | 400 |
| Unknown tenant | 404 |
| Inactive tenant | 403 |
| Registry unavailable | 503 (no fallback to another tenant) |
| Invalid or untrusted connection metadata | 500 "Tenant configuration error." |

Responses are RFC 7807 problem details and never include server names, database names or connection details.

### Stored procedures in migrations

Procedure definitions are version-controlled `.sql` files under
`src/MultiTenantDemo.Client.Data/Migrations/Sql/`, embedded in the assembly and loaded by an
explicit name through `EmbeddedSqlResource.Load("Customers/GetCustomerSummary.v1.sql")`, which throws if the
resource is missing or empty.

- Released files are immutable. A procedure change is a **new versioned file and a new migration**
  (`GetCustomerSummary.v2.sql` + `GetCustomerSummaryV2`), so editing SQL never silently alters a deployed
  database.
- Definitions run through `EXEC (N'...')` (`SqlDefinitionFromResource`) so each is its own batch. This also
  keeps `dotnet ef migrations script --idempotent` valid; without it the generated script puts
  `CREATE PROCEDURE` inside an `IF ... BEGIN` block, which SQL Server rejects.
- `Down()` restores the previous definition: `GetCustomerSummaryV2.Down` re-applies v1;
  `AddGetCustomerSummaryProcedure.Down` drops the procedure because none existed before it.

To revert a tenant database to an earlier procedure version, migrate it down to the migration that introduced that
version, either by running the generated `<MigrationId>.down.sql` files newest first, or with `dotnet ef`:

```bash
export MULTITENANT_DESIGNTIME_CONNECTION='Server=...;Database=MultiTenantDemo_TenantA;...'
dotnet ef database update AddGetCustomerSummaryProcedure $CLIENT   # GetCustomerSummary back to v1
dotnet ef database update InitialCreate $CLIENT                    # procedure dropped
dotnet ef database update $CLIENT                                  # forward to the latest version again
```

## Running locally

Prerequisites: .NET 10 SDK and Docker (or any disposable SQL Server 2016 SP1+).

```bash
# 1. A disposable SQL Server
docker run -d --name mtd-sql -e ACCEPT_EULA=Y -e 'MSSQL_SA_PASSWORD=<choose-a-local-password>' \
  -p 1433:1433 mcr.microsoft.com/mssql/server:2022-latest

# 2. The system database and the client databases
docker exec mtd-sql /opt/mssql-tools18/bin/sqlcmd -C -S localhost -U sa -P '<password>' \
  -Q "CREATE DATABASE MultiTenantDemo_System; CREATE DATABASE MultiTenantDemo_TenantA; CREATE DATABASE MultiTenantDemo_TenantB"

# 3. Apply the generated migration SQL yourself (dotnet run scripts/generate-migration-sql.cs)
SQLCMD="docker exec -i mtd-sql /opt/mssql-tools18/bin/sqlcmd -C -b -S localhost -U sa -P <password>"
$SQLCMD -d MultiTenantDemo_System  < migrations/system/idempotent.sql
$SQLCMD -d MultiTenantDemo_TenantA < migrations/client/idempotent.sql
$SQLCMD -d MultiTenantDemo_TenantB < migrations/client/idempotent.sql

# 4. Register the clients
$SQLCMD -d MultiTenantDemo_System -Q "INSERT INTO system.Tenants (TenantId, Name, ConnectionString, IsActive) VALUES
  ('tenant-a', 'Tenant A', 'Server=localhost,1433;Database=MultiTenantDemo_TenantA;User ID=sa;Password=<password>;TrustServerCertificate=True', 1),
  ('tenant-b', 'Tenant B', 'Server=localhost,1433;Database=MultiTenantDemo_TenantB;User ID=sa;Password=<password>;TrustServerCertificate=True', 1)"

# 5. Run the API (secrets via user secrets or environment variables, never appsettings)
export ASPNETCORE_ENVIRONMENT=Development
export SystemDatabase__ConnectionString='Server=localhost,1433;Database=MultiTenantDemo_System;User ID=sa;Password=<password>;TrustServerCertificate=True'
dotnet run --project src/MultiTenantDemo.Api   # http://localhost:5029
```

Tenant connection strings are validated against `TenantConnections:AllowedServers`, which is `localhost,1433` in
`appsettings.Development.json`. Set `IsActive` to 0 to suspend a tenant.

Then use `src/MultiTenantDemo.Api/MultiTenantDemo.Api.http`, or:

```bash
curl -X POST localhost:5029/api/customers -H 'X-Tenant-Id: tenant-a' -H 'Content-Type: application/json' \
  -d '{"name":"Ada","email":"ada@example.com"}'
curl localhost:5029/api/customers -H 'X-Tenant-Id: tenant-a'          # Ada
curl localhost:5029/api/customers -H 'X-Tenant-Id: tenant-b'          # []
curl localhost:5029/api/customers/summary -H 'X-Tenant-Id: tenant-a'  # runs dbo.GetCustomerSummary
```

## Migration commands

`dotnet-ef` is a local tool pinned in `dotnet-tools.json`; run `dotnet tool restore` once. The tool manifest has
no per-tool package source, so the repo-root `nuget.config` clears inherited sources and uses only nuget.org for
tool and package restore.

`dotnet-ef` 10 reads project metadata from `obj/project.assets.json` before it builds, so on a fresh clone (or
after deleting `obj`, or when restore fails) it stops with "Unable to retrieve project metadata. Ensure it's an
SDK-style project." even though every project is SDK-style. Run `dotnet restore MultiTenantDemo.sln` first;
`scripts/add-migration.cs` restores the startup project itself. If restore fails, the source in `nuget.config` is the
first thing to check.

`Microsoft.EntityFrameworkCore.Design` is referenced only by `MultiTenantDemo.Api`, so `MultiTenantDemo.Api` is the
startup project for every `dotnet ef` command and the Data project is the target project. All commands use the design-time factories `DesignTimeClientDbContextFactory` and `DesignTimeSystemDbContextFactory`. By default they point at a
non-resolvable host (`design-time.invalid`), so these work offline and **cannot touch a tenant database**.

```bash
CLIENT="--project src/MultiTenantDemo.Client.Data --startup-project src/MultiTenantDemo.Api"
SYSTEM="--project src/MultiTenantDemo.System.Data --startup-project src/MultiTenantDemo.Api"

# Add a migration
dotnet run scripts/add-migration.cs -- client <Name>
dotnet run scripts/add-migration.cs -- system <Name>

# Then regenerate the migration SQL (add -- --no-build to skip the build)
dotnet run scripts/generate-migration-sql.cs

# Check the model and migrations agree
dotnet ef migrations has-pending-model-changes $CLIENT

# List migrations without connecting
dotnet ef migrations list --no-connect $CLIENT

# The same from inside a Data project
cd src/MultiTenantDemo.Client.Data
dotnet ef migrations add <Name> --context ClientDbContext --startup-project ../MultiTenantDemo.Api
```

### Generated migration SQL

Migrations are created by hand during development with `dotnet run scripts/add-migration.cs -- <client|system> <Name>`, which
runs `dotnet ef migrations add` with the context's Data project as the target and `MultiTenantDemo.Api` as the startup project, then removes the
`// <auto-generated />` and `/// <inheritdoc />` lines (and the BOM) EF writes into the migration, designer and
snapshot files, since code carries no comments. The SQL files are then generated with
`dotnet ef migrations script` by `scripts/generate-migration-sql.cs`, which works offline (no database connection)
and writes:

| File | Generated with |
|---|---|
| `migrations/client/<MigrationId>.up.sql` | `dotnet ef migrations script <Previous> <MigrationId> $CLIENT` |
| `migrations/client/<MigrationId>.down.sql` | `dotnet ef migrations script <MigrationId> <Previous> $CLIENT` |
| `migrations/client/idempotent.sql` | `dotnet ef migrations script --idempotent $CLIENT` |
| `migrations/system/...` | The same three commands with `$SYSTEM` |

The script rebuilds each folder from scratch, so files for removed migrations disappear. The integration tests
apply the committed client migrations to every tenant database, and `ClientMigrationTests` walks
`dbo.GetCustomerSummary` down from v2 to v1 to nothing and back up, so CI fails if a migration or its `Down()` breaks. `migrations/` is git-ignored so the generated SQL
stays local. Both scripts are .NET 10 file-based apps, so they run the same way on Windows, macOS and Linux and need nothing
beyond the .NET 10 SDK.

To change a stored procedure: add `Sql/<Area>/<Name>.vN.sql`, reference it from `SqlScripts`, create an empty
migration with `migrations add`, call `migrationBuilder.SqlDefinitionFromResource(...)` in `Up()`, and restore
the previous version in `Down()`.

### Applying migrations

Nothing in the code applies migrations; the API never migrates. Apply them yourself, either with the generated
SQL (`idempotent.sql` applies only what is pending; the per-migration `up`/`down` files step one migration at a
time), or with EF directly:

```bash
dotnet ef database update $CLIENT \
  --connection 'Server=localhost,1433;Database=MultiTenantDemo_TenantA;User ID=sa;Password=<password>;TrustServerCertificate=True'
dotnet ef database update $SYSTEM \
  --connection 'Server=localhost,1433;Database=MultiTenantDemo_System;User ID=sa;Password=<password>;TrustServerCertificate=True'
```

Run the client migration once per client database.

## Tests

```bash
dotnet test MultiTenantDemo.sln
```

Tests start a disposable SQL Server 2022 container through Testcontainers. To use an existing disposable server
instead, set `MULTITENANT_TEST_SQLSERVER` to a server-level connection string; test databases (`mtd_*`) are
dropped at the end of the run.

| Acceptance criterion | Test(s) |
|---|---|
| Tenants resolve to different databases; resolution cached per request | `TenantRoutingApiTests.Tenants_resolve_to_different_databases`, `Resolution_is_cached_for_the_request` |
| Same request, different tenant, expected database; no cross-tenant visibility | `Data_written_for_tenant_A_is_only_visible_to_tenant_A` |
| Missing, malformed, unknown, inactive tenants and bad metadata fail closed; registry outage is 503 | `Invalid_tenant_requests_fail_closed`, `Registry_outage_returns_service_unavailable_without_falling_back`, `Untrusted_connection_metadata_fails_closed` |
| Procedure executes and maps | `Stored_procedure_executes_and_maps_its_result` |
| No secrets in logs or responses | `Api_logs_and_responses_never_contain_connection_secrets` |
| Embedded SQL loader, connection validation | `ComponentTests` |

## Known limitations and production hardening

- **Authentication and authorization** are absent; the tenant header is spoofable (see the warning above).
- **Tenant connection strings** are stored in plain text in `system.Tenants`. Production should store a secret
  reference (vault or managed identity) instead.
- **Credentials**: the POC carries a full connection string from the registry. Prefer managed identities or
  short-lived credentials from a vault, with a least-privileged login for the API (DML only) and a separate
  login for applying migrations (DDL).
- **Registry caching**: resolution is cached per request only; add a short-lived cache only if the registry's
  consistency guarantees allow it.
- **Connection pools**: one pool per tenant connection string. Very large tenant counts on one host need pool
  sizing review.
- **Observability**: default ASP.NET Core logging only. Metrics, tracing and alerting are not
  wired up.
